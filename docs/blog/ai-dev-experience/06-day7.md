### 프롬프트 (요약)

## 3. 타임아웃 + 에러 핸들링

### 프롬프트 (요약)

```
step3 진행 (에러 응답 정리 + 타임아웃 처리)
```

### AI가 생성한 코드

```java
// OkHttp 타임아웃
private final OkHttpClient client = new OkHttpClient.Builder()
    .connectTimeout(Duration.ofSeconds(10))
    .readTimeout(Duration.ofSeconds(30))
    .build();

// 타임아웃 전용 핸들러
@ExceptionHandler(SocketTimeoutException.class)
public ResponseEntity<Map<String, String>> handleTimeout(SocketTimeoutException e) {
    return ResponseEntity.status(HttpStatus.GATEWAY_TIMEOUT)
        .body(Map.of("error", "AI 서비스 응답 시간이 초과되었습니다."));
}
```

에러 계층 구조(400/502/504/500)를 자연스럽게 설계해줬다.

## 4. Turbopack 캐시 디버깅

### 상황

로컬에서 `npm run dev` 시 `Can't resolve 'tailwindcss'` 에러.

### AI의 디버깅 과정

1. turbopack root 설정 시도 → 실패
2. 루트 package.json 추가 시도 → 실패
3. `.next` 캐시 삭제 제안 → 성공

두 번 실패 후 근본 원인(캐시)을 짚었다. "설정 변경 후에도 캐시가 남아있을 수 있다"는 진단이 정확했다.

## Day 7 AI 활용 총평

| 작업 | AI 기여도 | 비고 |
|------|----------|------|
| 배포 환경 점검 | 100% | 코드 리뷰만으로 이슈 식별 |
| 입력 제한 | 100% | 백엔드+프론트 동시 생성 |
| 타임아웃 설정 | 100% | OkHttp + 핸들러 한 번에 |
| 캐시 디버깅 | 70% | 2번 실패 후 해결 |

### 오늘 배운 것

- **AI는 코드 리뷰 기반 잠재 이슈 식별을 잘한다.** "배포 환경 점검해줘"만으로 타임아웃, 길이 제한 문제를 찾아냈다.
- **빌드 캐시 문제는 AI도 바로 못 잡는다.** 환경 의존적 문제는 시행착오가 필요하다.
- **에러 계층 설계는 AI에게 맡기면 깔끔하게 나온다.** HTTP 상태코드 의미에 맞는 분류를 자연스럽게 해준다.
